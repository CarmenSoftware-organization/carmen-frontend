# Inventory Period: สร้างงวดถัดไปอัตโนมัติตอนปิดงวด + ห้ามแก้วันที่

วันที่: 2026-11-13 · ขนาดงาน: เล็ก (2 รีโป: `carmen-turborepo-backend`, `carmen-frontend`)

## เจตนา

วันที่ของงวดสต๊อกต้องมาจากระบบเท่านั้น ไม่มีใครพิมพ์หรือแก้ด้วยมือ
การปิดงวด (Period End) เป็นจุดเดียวที่ทำให้งวดใหม่เกิดขึ้น และต้องมีงวดเปิดล่วงหน้า
ครบ 12 เดือนเสมอ

## ที่ผู้ใช้ตัดสินแล้ว

- ปิดงวดแล้วระบบสร้างงวดถัดไปพร้อมวันที่เอง
- วันที่ของงวดห้ามแก้ไข
- มีงวดเปิดล่วงหน้าเสมอ 12 เดือน (เอกสารรับเข้าที่ลงวันที่เดือนถัดไปยังบันทึกได้ขณะงวดปัจจุบันยังไม่ปิด)

## เป้าหมาย / ไม่ใช่เป้าหมาย

- เป้าหมาย: หลังปิดงวดสำเร็จทุกครั้ง จำนวนงวดที่ยังไม่ปิด (open + locked) = 12
- เป้าหมาย: ไม่มีทางแก้ `start_at` / `end_at` / `fiscal_year` / `fiscal_month` ของงวดที่มีอยู่ ทั้งจากหน้าจอและจาก API
- ไม่ใช่เป้าหมาย: เปลี่ยนกติกาการปิดงวด การยกยอด หรือการพักรายการรอยกยอด
- ไม่ใช่เป้าหมาย: แก้ข้อมูลงวดเก่าที่วันที่ผิดรูปอยู่แล้วใน DB
- สิ่งที่ถือว่าล้มเหลว: ปิดงวดสำเร็จแต่งวดล่วงหน้าไม่ถูกเติม หรือการเติมงวดล้มเหลวแล้วงวดถูกปิดไปครึ่งทาง

## ทางเลือกที่พิจารณา

1. **เติมงวดใน transaction เดียวกับการปิดงวด (เลือก)** — `closeCurrent` เรียกตัวเติมงวดตัวเดียวกับปุ่ม "เติมรอบ" ด้วย `tx` เดียวกัน ปิดงวดกับเติมงวดสำเร็จหรือล้มเหลวพร้อมกัน ใช้ได้กับทุก client (เว็บ, mobile)
2. หน้าเว็บยิง `POST inventory-periods/next` ต่อหลังปิดงวดสำเร็จ — ไม่ต้องแก้ transaction แต่ไม่ atomic และ client อื่นที่ปิดงวดจะไม่เติมให้ ตัดทิ้ง
3. cronjob เติมงวดรายวัน — มีช่วงที่งวดไม่ครบ และเพิ่มชิ้นส่วนที่ต้องดูแล ตัดทิ้ง

## Backend (`apps/micro-business`)

- แยก logic เติมงวดใน `InventoryPeriodService.generateNextPeriods` ออกเป็นฟังก์ชันที่รับ Prisma client/transaction client (`tx`, `count`, `start_day`, `user_id`) แล้วให้ทั้ง endpoint เดิมและ `PeriodEndService.closeCurrent` เรียกตัวเดียวกัน
- `closeCurrent`: หลังเปลี่ยนสถานะเป็น `closed` (ใน transaction เดิม) เรียกตัวเติมงวดด้วย `count = 12`, `start_day = 1` ผลลัพธ์ใส่ใน response เป็น `periods_created`
- วันที่ของงวดใหม่ใช้กติกาเดิมของตัวเติมงวด: ต่อจากเดือนถัดจากงวดเปิดงวดสุดท้าย, `start_at` = วันที่ 1 (UTC), `end_at` = วันสุดท้ายของเดือน (UTC), รหัสงวด `YYMM`
- `InventoryPeriodService.update`: ถ้า payload ส่ง `start_at` / `end_at` / `fiscal_year` / `fiscal_month` ที่ **ต่างจากค่าเดิม** ให้ปฏิเสธด้วย error catalog ใหม่ `PERIOD_DATES_NOT_EDITABLE` (รูปแบบเดียวกับ `PERIOD_STATUS_VIA_PERIOD_END_ONLY`) ค่าที่เท่าเดิมผ่านได้ เพื่อไม่ทำ client เก่าที่ส่งกลับทั้งก้อนพัง; `note` / `info` / `dimension` ยังแก้ได้
- `create` (POST): อนุญาตเฉพาะเมื่อ BU ยังไม่มีงวดเลย (ตั้งงวดแรก) มีงวดอยู่แล้วให้ปฏิเสธด้วย error catalog ใหม่ `PERIOD_CREATE_ONLY_WHEN_EMPTY` *(ข้อนี้ผมตัดสินเอง)*
- เพิ่มข้อความ error ทั้งสองตัวใน `packages/error-catalog`

## Frontend (`routes/system-admin/inventory-period/`)

- หน้าเป็นแบบดูอย่างเดียว: ลบ `inventory-period-dialog.tsx`, `inventory-period-form-schema.ts`, ปุ่ม "เพิ่ม" และ hook create/update ที่ไม่มีผู้ใช้แล้ว
- รหัสงวดในตาราง การ์ดมือถือ และช่องในไทม์ไลน์ไม่เป็นปุ่มกดอีก *(ผมตัดสินเอง — ไม่มีอะไรให้เปิดดูเพิ่ม)*
- ปุ่ม "เติมรอบ" คงไว้ในเมนู ⋯ ใช้ตั้งงวดครั้งแรกของ BU ใหม่ และเติมให้ BU เดิมที่ตอนนี้มีไม่ถึง 12 งวด *(ผมตัดสินเอง)* empty state ชี้ไปที่ปุ่มนี้
- เพิ่มคำอธิบายสั้นใต้หัวหน้า: วันที่กำหนดโดยระบบ งวดใหม่ถูกสร้างเมื่อปิดงวด
- `useClosePeriodEnd` (`routes/inventory-management/period-end/use-period-end.ts`): เพิ่ม `QUERY_KEYS.INVENTORY_PERIODS` ใน `invalidateKeys` เพื่อให้หน้า Inventory Period เห็นงวดใหม่ทันที
- ข้อความแปลใหม่ทั้ง en/th; error catalog ฝั่ง FE ถ้ามีการแมปรหัส

## ลำดับ deploy

BE ก่อน FE (FE ขึ้นก่อนไม่พัง แต่งวดจะยังไม่ถูกเติมอัตโนมัติ) ไม่มี migration ไม่มี `api_name` ใหม่

## ที่เหลือให้คนลงมือ

- ชื่อและตำแหน่งของ helper ที่แยกออกมา
- รูป response ของ `closeCurrent` นอกเหนือจาก `periods_created`
- การตรวจมือ: ปิดงวดบน BU ทดสอบ (dev DB เป็นของร่วม — ใช้ T02) แล้วดูว่างวดเปิดครบ 12; ลอง PATCH วันที่ผ่าน curl ต้องได้ error
