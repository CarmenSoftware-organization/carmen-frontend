  • แต่ละสาขาคิดวิธีทำงานของตัวเอง ส่วนกลางจึงเปรียบเทียบต้นทุนข้ามสาขาไม่ได้ เพราะไม่มีมาตรฐานเดียวกันตั้งแต่ต้น

09

การรองรับหลายผู้เช่า

การแยกข้อมูลอยู่ในโครงสร้าง ไม่ใช่เงื่อนไขที่ใครสักคนต้องจำใส่

schema กลางเก็บตัวตน บทบาท และการสมัครใช้งาน ส่วนข้อมูลปฏิบัติการของแต่ละหน่วยธุรกิจอยู่ใน schema ของตัวเอง

  • ข้อมูลจะรั่วข้ามผู้เช่าได้ต้องพลาดถึงระดับ schema ไม่ใช่แค่ลืมใส่เงื่อนไขในคำสั่งค้นหา
  • สาขาเดียวสำรอง กู้คืน หรือย้ายได้ โดยไม่กระทบสาขาอื่นเลย
  • รายงานระดับเครือทำได้ โดยอ่านข้ามหน่วยธุรกิจตามสิทธิ์ของผู้เรียก ไม่ต้องเอาข้อมูลทุกผู้เช่ามากองรวมในตารางเดียว
  • การติดตั้งแบบผู้เช่าเดียวคือผลิตภัณฑ์ตัวเดียวกัน ไม่ใช่การแยกสายพัฒนา
10

ความปลอดภัยและตัวตน

ข้อมูลรับรองที่สำคัญที่สุด ไม่เคยถูกบันทึกลงดิสก์

  • access token อยู่ในหน่วยความจำเท่านั้น การอ่านที่เก็บข้อมูลของเบราว์เซอร์จึงไม่ได้อะไรที่เอาไปใช้ต่อได้
  • refresh token เป็นข้อมูลรับรองชิ้นเดียวที่ถูกเก็บ และการเพิกถอนทำที่ฝั่งเซิร์ฟเวอร์ การออกจากระบบจึงจบเซสชันจริง ไม่ใช่แค่ลบฝั่งเครื่อง
  • การยืนยันตัวตนมอบให้ผู้ให้บริการเฉพาะทาง Carmen Blue ไม่เคยเก็บรหัสผ่านเอง
  • สิทธิ์ผูกกับกลุ่มธุรกิจและหน่วยธุรกิจ บทบาทบอกว่าทำอะไรได้ ขอบเขตบอกว่าทำได้ที่ไหน
  • ความลับของการเชื่อมต่อถูกเข้ารหัสตอนพัก และไม่เคยถูกส่งกลับมาที่เบราว์เซอร์ ผู้ดูแลเปลี่ยนค่าใหม่ได้ แต่อ่านค่าเดิมไม่ได้
11

การตัดสินใจเชิงวิศวกรรม

สองภาษาโปรแกรม แต่ละภาษาอยู่ตรงที่มันคุ้ม

ภาษาใช้ตรงไหนทำไมต้องตรงนั้น
TypeScript API บริการต่าง ๆ และส่วนหน้าเว็บ ระบบชนิดข้อมูลชุดเดียวตั้งแต่ฐานข้อมูลถึงหน้าจอ การเปลี่ยนโครงสร้างเอกสารจะพังตอนคอมไพล์ ไม่ใช่พังต่อหน้าผู้ใช้
Go การสร้างรายงานและงานตามเวลา งานกินซีพียูและมาเป็นช่วง ๆ การรันรายงานปิดงวดต้องไม่ทำให้ครัวที่กำลัง ตั้งใบเบิกช้าลง จึงแยกทั้งด้วยกระบวนการและด้วยภาษาที่เลือกมาเพื่อรับโหลด

ไม่มีอะไรอยู่ในกองนี้เพราะมันใหม่

12

การขยายตัวและโครงสร้างต้นทุน

ชั้นที่ผู้ใช้ทุกคนแตะ ไม่มีเซิร์ฟเวอร์ให้ต้องจ่าย

  • ส่วนหน้าเว็บไม่ต้องขยาย เพราะมันคือไฟล์ ไฟล์นิ่งบน CDN รับผู้ใช้ที่เพิ่มขึ้นได้โดยไม่ต้องเพิ่มเครื่อง
  • API gateway ไม่ถือสถานะ จึงขยายแนวนอนหลังตัวกระจายโหลดได้
  • งานตามเวลาประสานกันผ่านการล็อกแบบกระจาย จึงรันหลายชุดพร้อมกันได้อย่างปลอดภัย งานหนึ่งงานมีเพียงชุดเดียวที่ทำ
  • ทราฟฟิกที่ผิดปกติถูกปฏิเสธที่ gateway ก่อนจะไปถึงบริการงานธุรกิจหรือฐานข้อมูล
  • schema แยกต่อหน่วยธุรกิจเป็นเส้นแบ่งที่พร้อมอยู่แล้ว ถ้าเครือใหญ่รายไหนต้องการฐานข้อมูลของตัวเอง

14

ข้อจำกัดของตลาด ที่แก้ไปแล้ว

เครือโรงแรมใหญ่ไม่ยอมเอาข้อมูลปฏิบัติการไปวางบนโครงสร้างที่ใช้ร่วมกับคนอื่น

รูปแบบลักษณะเปิดประตูอะไรให้
SaaS หลายผู้เช่าโครงสร้างใช้ร่วมกัน แยก schema ต่อผู้เช่าต้นทุนให้บริการต่ำที่สุด เหมาะกับโรงแรมเดี่ยวและเครือขนาดเล็ก
เซิร์ฟเวอร์ผู้เช่าเดียวระบบชุดเดิม บนโครงสร้างเฉพาะของลูกค้าเครือที่มีข้อกำหนดเรื่องที่อยู่ของข้อมูลหรือระเบียบจัดซื้อ
Docker imageทำงานได้ในตัว มี proxy ให้ API เองรันในระบบจัดการคอนเทนเนอร์ที่ลูกค้ามีอยู่ ไม่ต้องตั้งค่าข้ามโดเมน
ไฟล์นิ่งบน CDNส่วนหน้าเว็บวางบนที่เก็บไฟล์ส่งหน้าจอได้เร็วทั่วโลก ไม่ขึ้นกับว่า API อยู่ที่ไหน

ผลิตภัณฑ์ตัวเดียวกัน ต่างกันแค่การตั้งค่า ผู้ขายที่เสนอได้แค่ SaaS ใช้ร่วมกัน จะถูกตัดออกตั้งแต่ก่อนได้เข้าไปให้ประเมินโปรแกรม
